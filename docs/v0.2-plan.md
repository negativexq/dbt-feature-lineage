# v0.2 Plan — Artifact Engine

## Hedef

v0.1, `dbt_project.yml` + statik SQL taramasıyla (regex tabanlı `ref()`/`source()`
tespiti + sqlglot) çalışıyor. v0.2'nin hedefi, dbt'nin kendi derlediği
`target/manifest.json` ve `target/catalog.json` dosyalarını okuyarak daha
doğru ve zengin bir proje modeli üretmek — statik parser'ı **yedek** (fallback)
olarak korumak, birincil kaynak olarak artifact'ları kullanmak.

Kapsam:
1. `manifest.json` / `catalog.json` parser'ı
2. Artifact detector + fallback stratejisi (`dbt parse` tetikleme dahil)
3. Hem manifest hem static mod için ortak, normalize edilmiş internal proje modeli

Kapsam dışı (v0.2 sonrası): lineage graph görselleştirme değişiklikleri,
incremental/state karşılaştırma, çoklu proje desteği.

## 2. `manifest.json` / `catalog.json` parser'ı — `loaders/manifest_loader.py`

**Girdi:** `target/manifest.json` (zorunlu), `target/catalog.json` (opsiyonel —
sadece kolon tipleri/istatistikleri için, yoksa sessizce atlanır).

**Sorumluluklar:**
- `manifest.json`'ı yükle, `manifest_version`/`dbt_version` uyumluluğunu kontrol et
  (desteklenmeyen şema versiyonunda net bir hata/uyarı üret, sessiz geçme).
- `nodes` içinden `resource_type == "model"` olanları çıkar:
  - `compiled_code` / `raw_code` (dbt versiyonuna göre alan adı değişebilir —
    `compiled_sql`/`raw_sql` eski sürüm adları) → `DbtModel.raw_sql`
  - `depends_on.nodes` → `ref_dependencies` (model→model) ve
    `depends_on.nodes` içindeki `source.*` girdileri → `source_dependencies`
    (regex yerine doğrudan manifest'in çözdüğü bağımlılık grafiğinden okunur —
    v0.1'deki regex parser'ından çok daha güvenilir, çünkü manifest zaten
    Jinja'yı render etmiş ve macro/variable içeren `ref()` çağrılarını da çözmüş)
  - `path`/`original_file_path` → `file_path`/`relative_path`
  - `config.materialized`, `tags`, `schema`, `database` → `metadata` alanına
  - dizin bazlı layer tespiti yerine `fqn` (fully qualified name) veya path
    kullanılabilir; v0.1 ile tutarlılık için aynı `detect_model_layer()`
    mantığı `relative_path` üzerinde tekrar kullanılacak (kod tekrarı değil,
    `scanners/model_scanner.py`'daki fonksiyonun import edilip paylaşılması)
- `sources` içinden `DbtSource`/`DbtSourceTable` üret (manifest'teki `sources`
  key'i zaten dbt'nin çözdüğü hali; yaml_parser'daki mantığa paralel ama
  kaynağı farklı).
- `catalog.json` varsa: `nodes[].columns` içinden kolon adı+tipini oku, ileride
  `DbtModelAnalysis`'e "gerçek kolon tipi" bilgisi eklemek için ayrı bir
  opsiyonel alan/adapter olarak taşı (v0.2'de zorunlu değil, "varsa zenginleştir").

**Çıktı tipi:** Doğrudan `DbtProject` değil — bkz. Bölüm 4 (normalize model).
Bu modül ham manifest JSON'ını okuyup **ortak domain modeline** map eden bir
adapter olacak, kendi ayrı şema tipi üretmeyecek.

**Test edilebilirlik:** `examples/` altına küçük bir örnek `manifest.json`
fixture'ı eklenmeli (gerçek `dbt parse` çıktısından türetilmiş, anonimleştirilmiş).
Mevcut `examples/sample_banking_dbt` projesi için `dbt parse` çalıştırılıp
çıktısı `examples/sample_banking_dbt/target/manifest.json` olarak commit'lenebilir
— testler dbt CLI kurulu olmadan da manifest modunu doğrulayabilir.

## 3. Artifact detector + fallback stratejisi

Akış (yeni bir `loaders/project_loader.py` fonksiyonu veya onun önüne konan
bir orkestratör — bkz. Bölüm 5):

```
1. target/manifest.json var mı? (proje kökünde, configurable target path
   ileride — v0.2'de sabit "target/" yeterli)
   ├── VAR  → manifest_loader ile yükle
   │           ├── başarılı  → normalize edilmiş model, mode="manifest"
   │           └── parse hatası (bozuk/eksik JSON, şema uyumsuz)
   │                        → UI'da AÇIK uyarı göster + v0.1 static parser'a düş
   │                          (mode="static", reason="manifest_parse_failed: <detay>")
   └── YOK   → kullanıcıya onay iste: "Generate artifacts?" (bkz. altta)
               ├── kullanıcı ONAY VERMEDİ → doğrudan v0.1 static parser, mode="static"
               │                             (reason="user_declined")
               └── kullanıcı ONAY VERDİ
                   ├── `dbt` CLI PATH'te yok
                   │        → UI'da açık uyarı ("dbt CLI bulunamadı, kurulum:
                   │          <link/komut>") + static parser'a düş,
                   │          reason="dbt_cli_not_found"
                   └── `dbt` CLI var
                            → subprocess: `dbt parse --project-dir <path>
                              --profiles-dir <path?>` çalıştır
                              ├── exit code 0 ve manifest.json üretildi
                              │        → manifest_loader ile yükle, mode="manifest"
                              └── exit code != 0 veya manifest üretilmedi
                                       → UI'da stderr/özet ile açık uyarı +
                                         static parser'a düş,
                                         reason="dbt_parse_failed: <stderr özeti>"
```

**Tasarım kararları:**
- **Sessiz düşme yok.** Her fallback bir `ArtifactStatus`/`ArtifactWarning`
  nesnesi (mode, reason, detay mesajı) üretmeli ve bu, CLI'da `console.print`
  ile, Streamlit'te `st.warning`/`st.info` ile kullanıcıya gösterilmeli.
  Bu obje, normalize edilmiş proje modelinin bir parçası olarak taşınmalı
  (aşağıdaki `LineageSource`/`artifact_status` alanı), böylece hem CLI hem
  UI aynı bilgiyi tüketir — iki ayrı yerde aynı mantığı tekrar yazmaya gerek yok.
- **Onay akışı UI-agnostik olmalı.** Detector modülü kendi başına Streamlit
  veya typer'a bağımlı olmamalı; bir `should_generate_artifacts: bool` callback
  veya parametre alsın. CLI'da bu bir `--generate-artifacts/--no-artifacts`
  flag'i (veya interaktif `typer.confirm`) olarak; Streamlit'te bir buton/
  `st.confirm`-benzeri akış olarak karşılanır. Detector'ın kendisi "nasıl
  onay alındığı"nı bilmemeli.
- **subprocess güvenliği:** `dbt parse` çağrısı `shell=True` KULLANMAMALI,
  argüman listesi olarak çalıştırılmalı; proje path'i kullanıcı girdisi olduğu
  için (Streamlit'te text_input) path validasyonu (mevcut `load_dbt_project`
  zaten `resolve()` + `exists()` kontrolü yapıyor, aynısı burada da uygulanmalı)
  ve timeout (`subprocess.run(..., timeout=...)`) eklenmeli — kullanıcı rastgele
  bir path verirse `dbt parse` sonsuza kadar takılı kalmamalı ya da proje
  dizini dışında side effect yaratmamalı (dbt zaten kendi `--project-dir`
  scope'unda çalışır, ek bir sancaklama gerekmez ama timeout şart).
- **Cache:** `dbt parse` pahalı bir işlem; Streamlit tarafında zaten
  `@st.cache_data` kullanılıyor (`cached_load_project`), aynı pattern
  manifest moduna da uygulanmalı — ama manifest dosyasının `mtime`'ı cache
  key'ine dahil edilmeli, yoksa proje güncellenince stale sonuç dönebilir.

## 4. Normalize edilmiş internal proje modeli

Görevde "hem manifest hem static mode aynı domain modeline map olsun"
deniyor — **yeni bir domain tipi ailesi eklemek yerine mevcut
`domain/models.py` içindeki `DbtProject`/`DbtModel`/`DbtSource`/`DbtDependency`
tiplerinin genişletilmesi** öneriliyor, çünkü:

- `services/model_analysis_service.py` (`inspect_model`) ve `ui/rendering.py`
  zaten bu tiplere bağımlı; ayrı bir "ArtifactProject" tipi eklersek services/ui
  katmanında if/else dallanması veya ikinci bir adapter katmanı gerekir —
  gereksiz karmaşıklık.
- İki mod arasındaki fark sadece **kaynak** (nereden geldiği) ve **doğruluk
  derecesi** (regex-tahmini vs dbt-derlenmiş); şekil (shape) aynı kalmalı.

**Önerilen model değişiklikleri (`domain/models.py`):**
- `DbtProject`'e `source: Literal["manifest", "static"]` alanı eklenir
  (görevdeki "mode" bilgisi burada taşınır).
- `DbtProject`'e opsiyonel `artifact_status: ArtifactStatus | None` alanı
  eklenir — yeni küçük bir model: `mode`, `reason`, `message`, belki
  `dbt_version` (manifest modundaysa).
- `DbtModel`'e manifest-only alanlar opsiyonel olarak eklenir (hepsi
  `None`/boş default ile — static modda dolmaz, mevcut testleri bozmaz):
  `unique_id: str | None`, `materialization: str | None`,
  `compiled: bool = False`.
- `ref_dependencies`/`source_dependencies` şekli **değişmez** — manifest
  loader da aynı `DbtDependency` listesine map eder. Bu, tüm downstream
  (`query_flow_parser`, `inspect_model`, UI) kodunun değişmeden çalışmasını
  sağlayan en önemli karar.

**Neden `raw_sql` alanı manifest modunda da korunuyor:** `query_flow_parser.py`
(CTE/join/groupby analizi) SQL metnine göre çalışıyor. Manifest modunda
`compiled_code` (Jinja render edilmiş, ref/source'lar gerçek tablo adına
çözülmüş SQL) mevcut — bu aslında v0.1'in placeholder preprocessing'ine göre
**daha temiz bir girdi**. Öneri: manifest modunda `raw_sql` alanına
`compiled_code` konur ve `sql_parser.preprocess_dbt_sql` bu girdide zaten
Jinja kalmadığı için no-op'a yakın davranır (yine de dbt makrolarından artakalan
edge-case'ler için mevcut fallback regex'i koruma amaçlı çalışmaya devam eder).

## 5. Entegrasyon noktası — `project_loader.py`

Önerilen yaklaşım: `load_dbt_project()` imzasını bozmadan, önüne bir
**orkestrasyon fonksiyonu** eklemek:

```
loaders/project_loader.py
  load_dbt_project(path)               # v0.1 — DEĞİŞMEZ, static parser, geriye dönük uyumlu
  load_dbt_project_static(...)         # mevcut fonksiyonun yeniden adlandırılmış hali
                                        #   (opsiyonel — istenirse isim aynı kalabilir)

loaders/manifest_loader.py
  load_dbt_project_from_manifest(path) # yeni — manifest.json/catalog.json -> DbtProject

loaders/artifact_detector.py           # yeni — YÖNLENDİRME KATMANI
  resolve_dbt_project(
      path,
      confirm_generate: Callable[[], bool] | None = None,
  ) -> DbtProject                      # Bölüm 3'teki akışı yürütür, tek giriş noktası
```

- `cli.py` ve `app.py`, bugün doğrudan çağırdıkları `load_dbt_project(path)`
  yerine `resolve_dbt_project(path, confirm_generate=...)` çağırmaya geçer.
  Bu, iki çağıranı da minimal değiştirir (import + fonksiyon adı) ve asıl
  kararlılığı yeni modülde izole eder.
- Mevcut `load_dbt_project()` fonksiyonu **korunur** (import edilen yerlerde
  kırılma olmasın, ve `tests/test_project_loader.py` değişmeden geçsin diye).

## 7. Kararlar (v0.2)

1. **`dbt` CLI + `profiles.yml` kontrolü, `dbt parse` çağrısından önce
   `artifact_detector.py` içinde yapılır** (manifest_loader'ın sorumluluğu
   değil), sırasıyla:
   - `shutil.which("dbt") is None` → `dbt parse`'ı hiç çalıştırmadan
     `ArtifactStatus(mode="static", reason="dbt_cli_unavailable", ...)` ile
     static parser'a düş.
   - (CLI bulunduysa) proje kökünde `profiles.yml` yoksa, `DBT_PROFILES_DIR`
     altında da yoksa ve `~/.dbt/profiles.yml` da yoksa `dbt parse`
     çalıştırılmaz; yine sessizce değil,
     `ArtifactStatus(mode="static", reason="no_profile", ...)` ile static
     parser'a düşülür.
   - Her iki kontrol de `dbt parse` subprocess'i başlamadan **önce** yapılır,
     böylece gereksiz subprocess/timeout riski baştan elenir.

   Diğer fallback nedenleri (implemente edildi):
   `not_generated` (manifest yok, `generate_artifacts=False`),
   `dbt_parse_failed` (nonzero exit / timeout / manifest üretilmedi),
   `unsupported_manifest_schema_version`, `manifest_parse_failed`
   (bozuk JSON — hem mevcut hem yeni üretilen manifest için). Başarı
   durumunda `ArtifactStatus(mode="manifest", reason="found")` (zaten
   vardı) veya `reason="generated"` (`dbt parse` ile yeni üretildi).
2. **`manifest.json` şema versiyonu için desteklenen aralık sabit tutulur.**
   `loaders/manifest_loader.py` içinde `SUPPORTED_MANIFEST_SCHEMA_VERSIONS`
   sabiti (örn. `{"v11", "v12"}`) tanımlanır; `metadata.dbt_schema_version`
   URL'sinden (`.../manifest/v12.json`) çıkarılan versiyon bu kümede değilse
   `UnsupportedManifestSchemaVersionError` fırlatılır. Bu hata
   `artifact_detector` tarafından yakalanıp `ArtifactStatus(mode="static",
   reason="unsupported_manifest_schema_version", ...)` ile static parser'a
   düşürülür — sabit aralık, her yeni desteklenen dbt-core sürümünde
   bilinçli bir kod incelemesiyle genişletilir (otomatik/örtük genişleme yok).
3. **CLI onay akışı: `--generate-artifacts` flag'i + yoksa interaktif
   `rich.prompt.Confirm.ask()`.**
   - `--generate-artifacts` verilirse hiç sorulmadan `dbt parse` denenir.
   - `--no-generate-artifacts` (veya flag hiç verilmezse ve stdin TTY değilse,
     örn. CI) verilirse hiç sorulmadan static parser kullanılır.
   - Flag verilmemiş ve stdin interaktifse (`sys.stdin.isatty()`), kullanıcıya
     `Confirm.ask("target/manifest.json bulunamadı. `dbt parse` ile artifact "
     "üretilsin mi?")` ile sorulur.
   - Streamlit tarafında bu, ileride bir buton (`st.button`) ile karşılanacak
     (v0.2 kapsamında sadece CLI akışı netleştirildi; Streamlit onay UI'ı
     ayrı bir adımda ele alınacak).

## 8. `loaders/manifest_loader.py` — planlanan genel API (TDD referansı)

Aşağıdaki API, `tests/test_manifest_loader.py` tarafından sabitlenmiştir —
implementasyon bu sözleşmeye göre yazılacak:

```python
SUPPORTED_MANIFEST_SCHEMA_VERSIONS: frozenset[str]   # örn. {"v11", "v12"}

class ManifestNotFoundError(FileNotFoundError): ...
class ManifestParseError(ValueError): ...                    # bozuk JSON
class UnsupportedManifestSchemaVersionError(ValueError): ...  # aralık dışı şema

def load_dbt_project_from_manifest(
    project_path: str | Path,
    target_dir: str = "target",
) -> DbtProject: ...
```

Davranış özeti:
- `project_path/target_dir/manifest.json` yoksa → `ManifestNotFoundError`.
- JSON parse edilemiyorsa → `ManifestParseError`.
- `metadata.dbt_schema_version` desteklenen aralığın dışındaysa →
  `UnsupportedManifestSchemaVersionError`.
- `nodes` içindeki `resource_type == "model"` kayıtları `DbtModel`'e map
  edilir; `raw_sql` alanı **`compiled_code` varsa onu, yoksa `raw_code`'u**
  kullanır (not: `dbt parse` her zaman `compiled_code` üretmeyebilir —
  yalnızca `dbt compile`/`run`/`build` sonrası dolar; bu yüzden fallback
  zorunlu, sadece "varsa zenginleştir" değil).
- `depends_on.nodes` içindeki `model.*` girdileri ref bağımlılığına,
  `source.*` girdileri source bağımlılığına map edilir.
- `sources` içindeki kayıtlar `source_name`'e göre gruplanıp `DbtSource`/
  `DbtSourceTable`'a map edilir.
- Dönen `DbtProject.source == "manifest"`; `artifact_status` alanı
  `manifest_loader` tarafından **set edilmez** (`None` kalır) — o,
  `artifact_detector`'ın sorumluluğu (başarı/fallback durumunu bilen taraf
  o katman).
