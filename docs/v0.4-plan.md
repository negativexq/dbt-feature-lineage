# v0.4 Plan — Column Search + Lineage View

## Hedef

v0.3 ile `services/lineage_service.py::build_project_lineage(project)`
projedeki her model × her output kolonu için `ColumnNode`/`ColumnEdge`'lerden
oluşan tek bir `networkx.DiGraph` üretiyor (`lineage_cache_key()` ile
cache'lenebilir, `graph.graph["lineage_warnings"]` ile başarısız modelleri
sessiz değil açıkça raporluyor). v0.4'ün hedefi bu graph'ı **kullanılabilir**
hale getirmek: bir kolon adıyla arama yapıp, o kolonun **raw source'a kadar
olan upstream zincirini** hem CLI'da hem Streamlit'te göstermek.

Kapsam dışı (bilinçli): downstream/impact analysis (kimler bu kolonu
kullanıyor — roadmap'te ayrı madde), tam interaktif graph gezinme UI'ı
(zoom/pan/click-to-expand), kolon bazlı diff/versiyonlama.

## 2. Arama indeksi — nereye ait olmalı

**Öneri: `services/column_search.py` (yeni, ayrı dosya).**

Gerekçe: `schema_builder.py` (schema kurar), `lineage_service.py` (graph
kurar) desenini takip ederek, "kurulmuş graph'ı sorgula" da kendi başına
üçüncü bir concern. `lineage_service.py`'ye eklemek onu hem "graph'ı inşa
et" hem "graph'ı sorgula" sorumluluklarını taşıyan bir modül yapardı —
mevcut `parsers/` (sql_parser / query_flow_parser / dependency_parser /
yaml_parser) ve `loaders/` (project_loader / manifest_loader /
artifact_detector) ayrımlarıyla tutarsız olurdu. CLI ve Streamlit'in
ikisi de "ara → belirsizliği çöz → zinciri çek" akışını aynı şekilde
kullanacağı için, bu iki fonksiyonu (arama indeksi + upstream zincir)
**aynı modülde** birlikte tutmak mantıklı: birlikte "search & retrieve"
API'sini oluşturuyorlar.

```python
# services/column_search.py

def build_search_index(graph: nx.DiGraph) -> dict[str, list[ColumnNode]]:
    """{column_name: [ColumnNode, ...]} -- tam eşleşme, sıralı (model adına göre)."""

def get_upstream_chain(graph: nx.DiGraph, target: ColumnNode) -> list[ColumnNode]:
    """target dahil, raw source'tan target'a doğru topolojik sıralı ata listesi."""
```

`build_search_index` **tam eşleşmeli** bir index üretir (kolon adı ->
o adı taşıyan tüm `ColumnNode`'lar). Alt-string/case-insensitive arama
UI katmanında yapılır — mevcut `ui/rendering.py::filter_models`/
`filter_output_columns` deseniyle birebir tutarlı (`[key for key in
index if search_term.lower() in key.lower()]`), yeni bir arama
soyutlaması icat etmeye gerek yok.

## 3. Upstream zincir çekme

```python
def get_upstream_chain(graph: nx.DiGraph, target: ColumnNode) -> list[ColumnNode]:
    ancestors = nx.ancestors(graph, target)  # target'a giden tüm yollar
    subgraph = graph.subgraph({*ancestors, target})
    return list(nx.topological_sort(subgraph))
```

`graph`'taki kenarlar `ColumnEdge(source=upstream, target=downstream)`
yönünde kuruldu (v0.3), yani `nx.ancestors(graph, target)` doğrudan
"target'ın upstream'inde olan her şey" kümesini veriyor — ekstra ters
çevirmeye gerek yok. `nx.topological_sort` bu induced subgraph üzerinde
çalıştırılınca "en yukarı akıştaki (raw source'a en yakın) önce" sırasını
veriyor — v0.3'ün döngü koruması (`_guard_against_circular_dependencies`)
sayesinde bu subgraph'ın DAG olduğu zaten garanti.

**Önemli nüans — zincir her zaman DOĞRUSAL değil.** Görev tanımı "raw
source -> ... -> hedef kolon" diyor ve bu, `coalesce()`/join gibi **birden
fazla upstream girdisi olan** kolonlar için yanıltıcı olabilir (örn.
`account_count = coalesce(a.account_count, ar.raw_account_count, 0)` iki
farklı upstream'den besleniyor — bkz. v0.3'te düzeltilen gerçek
`mart_customer_features` örneği). Bu durumda `topological_sort` sonucu
düz bir liste verir ama alt-graph aslında **dallanan bir DAG**'tır, tek
bir ok zinciri değil. Öneri: CLI'da varsayılan gösterim "her kenarı
topolojik sırayla listele" (Bölüm 5) — hem doğrusal hem dallı durumda
doğru çalışır; Streamlit'te `st.graphviz_chart` zaten native DAG çizdiği
için bu sorun yok (Bölüm 6).

## 4. CLI: `lineage` komutu

Mevcut `analyze`/`inspect` deseniyle tutarlı: `project_path` ilk argüman,
`--json` bayrağı `_build_output_payload`/`typer.echo(json.dumps(...))`
deseniyle aynı, Rich `Table`/`Panel` kullanımı `_render_model_inspection`
ile aynı stil.

```python
@app.command()
def lineage(
    project_path: str = typer.Argument(...),
    column_name: str = typer.Argument(..., help="Column name to trace."),
    model_name: str | None = typer.Option(
        None, "--model", help="Disambiguate when multiple models have this column."
    ),
    json_output: bool = typer.Option(False, "--json"),
) -> None:
    resolved_path = Path(project_path).expanduser().resolve()
    project = resolve_dbt_project(resolved_path, generate_artifacts=False)
    graph = build_project_lineage(project)
    index = build_search_index(graph)

    matches = index.get(column_name, [])
    target = _resolve_ambiguous_match(matches, model_name)  # bkz. altta
    chain = get_upstream_chain(graph, target)
    ...
```

`--generate-artifacts` bilinçli olarak **eklenmiyor** — `inspect` komutu
da eklemedi (v0.2/v0.3 entegrasyon turunda), tutarlılık için aynı minimal
deseni koruyoruz (manifest zaten diskteyse otomatik kullanılıyor,
`resolve_dbt_project`'in kendi önceliklendirmesi sayesinde).

**Belirsizlik çözümü** (`_resolve_ambiguous_match`):
- 0 eşleşme → `typer.echo` ile "kolon bulunamadı", `raise typer.Exit(1)`.
- 1 eşleşme → doğrudan kullan.
- >1 eşleşme ve `--model` verilmişse → o modele filtrele; yine 0 ya da
  >1 ise hata.
- >1 eşleşme, `--model` verilmemiş, `_is_interactive()` (mevcut
  `cli.py::_is_interactive`, zaten var) → `rich.prompt.Prompt.ask("Which
  model?", choices=[m.model for m in matches])` ile sor (mevcut
  `Confirm.ask` desenine paralel, ama string seçim için `Prompt.ask`).
- >1 eşleşme, non-interactive (CI/pipe) → eşleşen tüm `(model, layer)`
  çiftlerini listele, `--model` ile tekrar çağırmasını söyle, exit(1) —
  `_resolve_generate_artifacts`'in "non-interactive'de asla sorma"
  ilkesiyle tutarlı.

**Metin çıktısı:** görev "raw_source.col -> ... -> mart.col" formatını
istiyor — Bölüm 3'teki doğrusal-olmayabilir nüansı nedeniyle, her kenarı
ayrı satırda `transformation_type` etiketiyle göstermeyi öneriyorum
(doğrusal zincirde bu zaten yukarıdan aşağı tek bir ok dizisi gibi okunur,
dallı durumda da doğru kalır):

```
raw_banking.customers.customer_id
  -> stg_customers.customer_id            [direct]
  -> int_customer_activity.customer_id    [direct]
  -> mart_customer_overview.customer_id   [direct]
```

`--json` çıktısı `_build_output_payload` deseniyle tutarlı: `{"column":
..., "model": ..., "chain": [{"model":, "column":, "layer":}, ...],
"edges": [{"source":, "target":, "transformation_type":,
"expression_sql":}, ...]}`.

## 5. Streamlit: 5. sekme — "Column Lineage"

```python
overview_tab, flow_tab, columns_tab, raw_sql_tab, lineage_tab = st.tabs(
    ["Overview", "Query Flow", "Columns", "Raw SQL", "Column Lineage"]
)
...
with lineage_tab:
    graph = cached_build_project_lineage(str(resolved_path), _manifest_cache_key(resolved_path), lineage_cache_key(project))

    if graph.graph.get("lineage_warnings"):
        with st.expander(f"{len(graph.graph['lineage_warnings'])} model(s) excluded from lineage"):
            for warning in graph.graph["lineage_warnings"]:
                st.warning(warning)

    search_term = st.text_input("Search for a column", value="", key="lineage_search")
    index = build_search_index(graph)
    matches = [
        node for name, nodes in index.items()
        if search_term and search_term.lower() in name.lower()
        for node in nodes
    ]

    if matches:
        selected_label = st.selectbox(
            "Select a match",
            options=[f"{n.model}.{n.column} ({n.layer})" for n in matches],
        )
        target = matches[[...].index(selected_label)]
        chain = get_upstream_chain(graph, target)
        st.graphviz_chart(_to_dot(graph.subgraph(chain)))
```

**Bu sekme sidebar'daki "seçili model"den bağımsızdır** — kendi arama
kutusuna sahip, proje geneli çalışır (Bölüm 1'deki gözlemin doğal
sonucu). Bu, dört mevcut sekmenin davranışından **kasıtlı bir sapma**;
kullanıcı kafa karışıklığını önlemek için sekme başlığında ve/veya bir
`st.caption("Searches the whole project, not just the model selected in the sidebar.")`
ile açıkça belirtilmeli.

**`st.graphviz_chart` — yeni bağımlılık gerektirmiyor.** `graphviz`
Python paketi kurulu değil (kontrol ettim) ve eklemeyi önermiyorum —
`st.graphviz_chart` bir DOT-format **string** de kabul ediyor (dokümante
edilmiş davranış), bu yüzden `networkx` graph'ından elle küçük bir DOT
string üreten bir `_to_dot(subgraph) -> str` yardımcı fonksiyonu yeterli
(node etiketleri `model.column`, kenar etiketleri `transformation_type`).
`pydot`/`pygraphviz` gibi networkx'in DOT-export yardımcıları da ek
bağımlılık istediği için tercih edilmiyor.

## 6. Cache deseni — v0.2/v0.3 ile birebir aynı yaklaşım

v0.2'nin `cached_load_project(project_path: str, manifest_cache_key:
float)` deseni: cache-busting anahtarı **dışarıda, ucuz bir şekilde**
hesaplanır ve cached fonksiyona **primitif** (hashable) bir argüman
olarak geçilir; fonksiyonun kendisi asıl pahalı objeyi TAZE kurar (ya da
başka bir cache'li çağrıyı kullanır). Aynı desen lineage için:

```python
@st.cache_data(show_spinner=False)
def cached_build_project_lineage(
    project_path: str, manifest_cache_key: float, lineage_key: tuple
) -> nx.DiGraph:
    project = cached_load_project(project_path, manifest_cache_key)
    return build_project_lineage(project)
```

`lineage_key = lineage_cache_key(project)` (v0.3'te zaten var, saf
fonksiyon) `main()` içinde `project` zaten yüklendikten sonra ucuzca
hesaplanıp cached fonksiyona geçilir. `project`'in kendisini DOĞRUDAN
cache anahtarı/argümanı yapmıyoruz — pydantic modelinin Streamlit'in
kendi hash mekanizmasıyla nasıl davranacağı belirsiz (muhtemelen çalışır
ama yavaş/kırılgan olabilir), v0.2 hiç bu riske girmedi, biz de girmeyelim.
`cached_build_project_lineage` içeride `cached_load_project`'i tekrar
çağırmak REDUNDANT görünebilir ama kendisi de cache'li olduğu için pratikte
anlık bir cache-hit; asıl amaç `project` objesini HER ZAMAN doğru/taze
kaynaktan almak.

İlk yükleme (cache miss) v0.3'te 12 modelli örnek projede **~15 saniye**
sürdü (ölçüldü) — `st.spinner("Building lineage graph...")` ile sarmalanmalı,
v0.2'deki `dbt parse` spinner'ıyla aynı desen.

## 7. Riskler

1. **Büyük graph'larda görselleştirme performansı.** `st.graphviz_chart`
   dagre-d3 kullanıyor; onlarca upstream dalı olan bir kolon (çok sayıda
   join/coalesce) görsel olarak okunaksız VE tarayıcıda yavaş render
   olabilir hale gelebilir. Ölçüm yapılmadı (v0.3'ün 4-seviyeli test
   fixture'ı küçük). Öneri: subgraph düğüm sayısı bir eşiği (örn. 50)
   aşarsa `st.warning(f"Chain has {n} nodes — rendering may be slow")`
   göster; tam çözüm (budama/sayfalama) v0.4 kapsamı dışına bırakılabilir.
2. **Aynı isimli kolon birden fazla modelde.** `customer_id` gibi yaygın
   isimler onlarca modelde görünebilir. CLI'da `--model` zorunlu hale
   gelmeden önce interaktif `Prompt.ask` ile listelemek (Bölüm 4) makul;
   ama liste kendisi de uzun olabilir (örn. 12 modelde `customer_id`
   varsa) — CLI çıktısı `layer`'a göre gruplanarak gösterilebilir
   (staging/intermediate/marts). Streamlit'te `st.selectbox` doğal olarak
   ölçekli (arama/scroll destekli), bu risk orada daha az kritik.
3. **`lineage_warnings` nerede gösterilmeli.** Karar: **sadece yeni
   "Column Lineage" sekmesinde**, `st.expander` içinde (Bölüm 5) —
   diğer 4 sekme `inspect_model`'i kullanıyor, `build_project_lineage`'e
   hiç dokunmuyor, oralarda göstermek ilgisiz gürültü olurdu. Tek
   istisna değerlendirildi ama ERTELENDİ: sidebar'da seçili modelin
   kendisi `lineage_warnings` listesinde geçiyorsa Overview sekmesinde
   de küçük bir not göstermek — bu, "Column Lineage" sekmesine hiç
   girmemiş bir kullanıcının o modelin lineage'inin neden eksik
   olduğunu asla öğrenememesi riskini azaltır, ama v0.4'ün ilk turunda
   scope'u genişletmemek için ERTELENDİ (v0.4.1 adayı).
4. **Zincirin doğrusal olmadığı durumlar (Bölüm 3).** CLI/UI tasarımı
   bunu ele alacak şekilde seçildi (kenar listesi / native DAG
   render) ama kullanıcı beklentisi hâlâ "tek bir ok zinciri" olabilir;
   ilk kullanımda kafa karıştırabilir. Mitigasyon: CLI çıktısında
   dallanma varsa (bir düğümün subgraph içinde birden fazla downstream
   kenarı varsa) küçük bir not eklenebilir ("this column has multiple
   upstream inputs") — v0.4 implementasyon detayı.
5. **`st.cache_data`'nın `nx.DiGraph` + pydantic `ColumnNode` düğüm
   anahtarlarını pickle edebilmesi varsayılıyor, doğrulanmadı.** Pydantic
   v2 modelleri genelde picklable, düşük risk, ama implementasyon
   sırasında ilk doğrulanacak şey bu olmalı (cache gerçekten hit alıyor
   mu, yoksa her rerun'da sessizce yeniden mi kuruluyor).
6. **Performans: CLI'da her `lineage` komutu tüm proje graph'ını sıfırdan
   kuruyor** (v0.3 planının zaten kabul ettiği bir ödünleşim — CLI
   process-ömrü kısa, cross-invocation cache yok). 12 modelli örnek
   projede ~15 saniye — kullanıcı tek bir kolonun zincirini görmek için
   TÜM projenin lineage'inin kurulmasını bekliyor. v0.4 kapsamında
   çözülmüyor (bkz. Açık sorular).
